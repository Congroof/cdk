# SkinForge 双后台发布与服务迁移

旧入口：`http://62.234.58.74/api`。新入口：`http://47.122.109.156/api`。

## 1. 已确认的方案

```text
旧客户端 -> 旧 cdk-server 检查更新 -> 同一份新版安装包
新版客户端（安装/重启后） -> 新 cdk-server
```

- 新版同时在新、旧后台可见，版本号、安装包、签名保持一致。
- 旧 cdk-server 保持原业务代码和 HTTP/WebSocket 路由，不升级旧服务代码，
  不增加迁移代理或重定向。旧机器保留剩余约 20 天，继续服务未升级用户。
- 新版的 CDK、公告、反馈、Mod、WebSocket、Hash 和 Updater 都直连新入口，
  不自动回退旧 IP；原有签名私钥和客户端公钥保持匹配。
- 本文是人工部署清单；本地仓库改动不等于已迁移线上数据库、配置或发布版本。

## 2. 统一数据库，不运行两份独立写入源

双后台发布只保证更新信息可见，**不会自动同步 CDK、绑定、续期、封禁或反馈**。
低改动方案是把完整数据库迁至新服务器，让两个服务共用迁移后的数据库。
旧服务只调整 `DATABASE_URL` 等必要部署配置并重启，不改业务代码。

1. 备份完整 MySQL 数据库和实际部署配置。库内包含用户、CDK、绑定历史、封禁、
   反馈、公告、云文档设置、软件发布、Mod、Hash 发布和同步状态。
2. 现有 `deploy/migrate-export.sh` 是不停服的一致性快照，导出开始后的写入
   不在备份中。选择短暂停写后做最终导出，或先完成增量追平再切换，避免丢失
   过渡期间的激活、续期和绑定数据。不要让旧库继续接收最终快照之后的写入。
3. 导出脚本实际只打包 SQL，尽管原注释提到 `.env`；环境变量、密钥和 Hash
   staging 需另外安全迁移。脚本的 Docker 数据库密码需与实际部署相符。
4. 新机器导入前确认备份和目标库，导入会覆盖已有数据，导入期间停用目标应用。
5. 新服务先连接迁移后数据库并校验数据，再在切换窗口把旧服务的连接指向同一库。
   Compose/根目录 `.env` 与 systemd 的 `EnvironmentFile` 按实际部署分别设置。
   旧服务仍保留并运行，不执行“停止旧服务后仅保留代理”的流程。
6. 数据库通过私网或只允许旧服务器来源的受限连接访问；不向任意来源开放 3306。
   Compose 内 `mysql:3306` 仅对本 Docker 网络有效，旧机器需填写可达的受限地址。
7. 新旧服务使用相同的原 `KDOCS_CREDENTIAL_KEY`，以解密库内云文档 Cookie。
   如需延续原 JWT 验证能力，保留 `JWT_SECRET`。密钥不写入 Git、工单或公开日志。
8. 只保留一个 Hash 定时同步实例。若旧部署支持此变量，在旧服务设置
   `SKINFORGE_HASH_SYNC_ENABLED=false`，由新服务负责同步；这不影响旧端读取
   已发布的 Hash 元数据。检查新 staging 目录的权限、挂载及未完成上传状态。

旧服务的实际版本需支持当前发布清单和数据库 schema；部署前验证兼容性。
若坚持独立数据库，需要另行设计持续数据同步；仅分别导入安装包清单并不足够。

## 3. 同一个新版在两个后台可见

1. 在 SkinForge 提升版本，使用原 Updater 私钥执行构建与签名。
2. 上传一次安装包和签名对应的发布清单，获得 `skinforge-release.json`。
3. 在一个后台导入清单并发布，然后登录另一个后台确认相同记录可见。
4. 分别访问新、旧 updater endpoint，确认低版本请求均返回同一版本和签名，
   最终安装包是同一份。两次解析得到的临时 OSS URL 可以不同，不要求 URL 字符串相等。

**共库时只需导入一次。** `skinforge_releases` 的当前版本是全局记录（id=1），
两个后台自然读取同一条发布数据；重复导入同版本会因版本必须严格递增返回 409。
这不是发布失败，也不需要为另一个后台额外增加一次版本号。

只有独立发布数据库才需要分别导入同一清单，并确保云文档目录、凭据和签名一致；
但这种做法本身不解决第 2 节的业务数据一致性问题。

## 4. 验证与边界

分别检查旧、新两个 HTTP 入口；不要只测试新服务器首页。

```bash
curl -i http://62.234.58.74/api/client/skinforge/update/windows/x86_64/1.0.0
curl -i http://47.122.109.156/api/client/skinforge/update/windows/x86_64/1.0.0
```

- 低于发布版本时，两端返回顶层版本 JSON、同一版本、签名和可用的 HTTPS OSS
  下载地址；用已发布版本请求应返回 204。尚未发布时也返回 204，需区分检查。
- 测试 CDK 在旧端与新端读取同一有效期、机器绑定和封禁状态；检查公告、反馈、
  Mod、Hash 等数据。Hash 的 gzip/identity 临时下载地址均需可用。
- 用真实旧客户端从旧后台完成更新下载、签名验证、安装和重启，确认新版的
  HTTP 与 WebSocket 请求直接连接新 IP，无需旧地址代理。
- 新旧管理后台的浏览器 localStorage 不共用，访问新后台需重新登录。
- 不记录 CDK、机器码、Cookie 或完整临时下载 URL。

**共库不是完整的多实例会话集群。** 当前 WebSocket 连接注册表在各服务进程
内存中，跨实例的即时换绑/封禁推送和在线统计不会仅因共库而自动统一。
迁移时应使用测试 CDK 验证这一边界；旧客户端升级、重启或重新校验时以数据库
状态为准，不把本方案描述为跨节点即时踢下线。跨实例即时推送改造不在本次范围。

## 5. 到期下线与回滚

在约 20 天的窗口内尽早发布并通知用户升级，持续检查旧端请求和活跃连接，
预留最后的升级缓冲。旧服务器到期后，尚未升级的客户端需要另行下载安装新版；
已经升级的客户端继续连接新入口。

下线旧机器前确认新服务、数据库、密钥和 Hash staging 已独立就绪，新服务不依赖
旧机器存储。发生回滚时优先保留新数据库为权威源，只回滚应用/发布配置；
已有新写入时不恢复旧快照。确需回迁数据，先暂停写入并完成反向同步与校验。

`skinforge-updates/latest.json` 是历史静态发布记录，当前动态接口不读取它。
本次不改写历史版本，不新增旧地址代理，也不修改现有导出脚本。

## GameHash 云端对象覆盖修复

已观察到新旧后台给出不同的 gzip/TXT 大小和摘要，却指向同一组云端对象。
这会造成旧元数据下载到新字节，出现 gzip 大小不一致及 identity 超过声明大小。
新服务器需部署本次 Hash 同步修复（旧服务器业务代码保持不变）：

1. 保留原数据库、密钥与私有 staging；部署新后端并重启。
2. 新端启动同步或后台手动触发 Hash 同步。即使版本未变，也会把旧固定名记录
   修复为每个文件独立 SHA-256 命名的对象，上传 TXT/gzip 成功后原子发布。
3. 确认两端不再共享被不同内容覆盖的对象，使用客户端下载并验签/校验 Hash。
   不通过修改数据库声明大小或关闭客户端 SHA 校验来掩盖错误。
4. 单纯发布新版客户端不会修复云端发布记录；需完成新端同步。

修复前的旧元数据若已被覆盖，旧客户端的更新仍可能失败；已有本地字典保持可用，
旧版软件仍可通过独立的软件更新接口升级到直连新端的新版。
